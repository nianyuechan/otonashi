## 3. 可维护性与规范性评估

结论：**当前重构方向是对的，但仅凭“Go 化 + 三模块拆分”不能保证可维护性和规范性。** 现在具备基础，不足以称为有保证；需要把下面几项固化成工程约束。

### 3.1 已有的基础

- `go-yunzai` / `go-render` / `bench` 三个模块边界清晰，`internal` 与 `pkg` 分层，`go-render` 作为独立服务有 HTTP 层与渲染层分离；
- 统一验证入口 `scripts/Test-Go.ps1` 覆盖 gofmt/test/build/vet；
- loadgen 有 `ProtocolVersion` 和结果 JSON 自记录参数；
- 插件 SDK、配置、存储、渲染客户端都有测试与 README；
- 本轮审查已把生产代码与测量代码分开，证据目录和报告路径开始集中。

### 3.2 目前不能保证的地方

- **验证入口不完整**：`bench/tools/sqlite-diag` 是独立模块，不被 `Test-Go.ps1` 覆盖；没有 CI，当前 HEAD 也缺一次统一入口整跑。
- **结果契约没有冻结**：`summary` 字段靠代码直接扩展，缺少结果 schema、字段版本和兼容性测试；`missing_replies` 的覆盖范围就因此被误读。
- **证据治理不足**：固定 `run.err` 会被下一轮覆盖；`.gitignore` 的 `*.log` 会让新日志默认不入库；存储侧原始 stderr 已无法追溯。
- **文档不是单一事实源**：归档后仍有 `bench/reports/...` 旧路径；目标表、报告和 handoff 的轮次数曾不一致。
- **脚本承担过多逻辑**：PowerShell 负责构建、启动、采样、清理、结果校验，参数与失败路径多；缺少统一 CLI/测试。
- **可观测性缺口**：go-render 没有 pprof/goroutine 快照通道，渲染器有界性无法验证；“goroutine 恒 9”曾误归因。
- **安全与运行边界**：go-render 端点无鉴权、无出站隔离；这些属于 M7，但必须在设计上保持显式待办，不能默认安全。
- **测试环境不稳定**：本机 IO 停滞、提交限额和长测试导致结果依赖环境；需要固定资源预算、缩短关键测试或分层运行。

### 3.3 要形成“可保证”的最低条件

1. 一个统一入口覆盖全部模块（含 `sqlite-diag`），并在 CI 或固定本地窗口连续通过；
2. 结果 JSON 有 schema/字段版本，新增字段有兼容性测试；
3. 证据按“结果名 + 运行名”留存，日志不被覆盖，关键证据可入库；
4. 文档只有一个事实源：`docs/` 下的 plan、baseline、index 与代码路径一致；
5. 测量代码和生产代码分离，测量口径有单元测试和 runbook；
6. 渲染器有 opt-in 的 pprof/快照；安全边界（鉴权、出站隔离）有明确里程碑；
7. 每个 P1/P2 修复都有独立提交、复现步骤和验收证据。

满足这些条件后，可以说“方向可维护、过程可审计”；在这之前，准确说法是“方向正确，基础具备，但还没有制度化保证”。
